## Lancer

Self-hosted platform that deploys apps into the user's own AWS account, cheaper than Render or Heroku. TypeScript on Node, pnpm workspace: Pulumi Automation API for AWS, Fastify + Drizzle/SQLite API, React dashboard, Next.js/Fumadocs website. Only the installer path is wired today (foundation stack + Lancer API service); `createStaticSite`, `createDatabase` and `createCache` exist but nothing calls them. Planning lives in `_bmad-output/`, project docs in `docs/`, public docs in `packages/website/content/docs/`.

## Policy

- Never run the installer without `--dry-run`: a real run creates billed AWS resources. Use `pnpm --filter @lancer/installer start`, which passes it.
- Never put a real AWS key, token, password or account ID in code, tests, fixtures, issues or commits; make them up, as the fixtures in `packages/api/src/modules/*/fixtures/` do.
- Commit messages: plain imperative English, no `feat:`/`fix:` prefix, never mention Claude or any AI tool, no `Co-Authored-By` or "Generated by" line.
- YAGNI: no speculative code, abstraction or dependency before a feature needs it.
- The existing code is an early prototype, not the standard to copy. When a change needs new structure, use an established pattern from comparable mature projects, classes included where they model the domain, and name the pattern in the pull request. Conventions below change through `bmad-architecture`, then in this block.
- Keep the cost model: no NAT Gateway (public subnets and security groups instead), Graviton `t4g` instances, one ALB shared by all services, Valkey rather than Redis.
- Databases and caches accept traffic only from the ECS security group; never expose them publicly.
- Never hand-edit `packages/dashboard/src/lib/api/` or `packages/api/openapi.json`: both are generated and gitignored.

## Where things are

- API: entry `packages/api/src/main.ts` (port 3141); app, plugins and module registration in `packages/api/src/modules/app.module.ts`.
- Installer: flow in `packages/installer/src/main.ts`, steps in `src/steps/`, bootstrap shell in `scripts/install.sh`.
- AWS components: `packages/infrastructure/src/providers/aws/`; `lancer-api.ts` deploys Lancer itself. `CloudProvider` in `providers/index.ts` is the provider contract; its AWS implementation is a stub.
- Values shared by API, dashboard and installer (AWS regions): `packages/shared/src/constants/`.

## Running and verifying

- Use Node 22.18 or later: the API runs `.ts` files directly (`node src/main.ts`) without a flag.
- There is no root `test` script: run `pnpm --filter @lancer/api test` and `pnpm --filter @lancer/infrastructure test`.
- `pnpm typecheck` checks only `packages/api`; check the dashboard with `pnpm --filter @lancer/dashboard build`.
- Before building the dashboard or running its e2e tests, and after changing an API route: `pnpm --filter @lancer/api generate:openapi`, then `pnpm --filter @lancer/dashboard generate:openapi`.
- Dashboard e2e tests start Vite only and stub the API with orval's MSW mocks; no API server needed.
- Nothing applies Drizzle migrations at runtime and the workflow (`drizzle-kit push` or `migrate`) is undecided; ask before choosing one. Generate a migration with `pnpm --filter @lancer/api exec drizzle-kit generate` after editing a `*.schema.ts`.

## Conventions that differ from defaults

- Relative imports carry the `.ts`/`.tsx` extension; type-only imports use `import type` (`verbatimModuleSyntax`).
- Erasable TypeScript only, since Node strips types without compiling: no `enum`, `namespace` or constructor parameter properties; use `as const` objects and explicit field assignments.
- API module in `packages/api/src/modules/{name}/`: `{name}.module.ts` registers its controllers under a sub-prefix and is registered in `app.module.ts` under `/api`; `controllers/{action}.controller.ts`; `services/{name}.service.ts` as plain exported functions imported as `* as xService`; database access only in `adapters/*.adapter.ts`; `entities/*.entity.ts` with a `toX()` mapper; `dtos/{action}.request.ts` and `.response.ts` as Zod schemas plus `z.infer` types.
- Every route declares `schema.tags` and `schema.operationId`, and its tag is declared in the swagger config of `app.module.ts`: orval names the dashboard hooks from them.
- Throw the `HttpException` subclasses of `common/exceptions/http.exception.ts` from controllers, guards and hooks only; services return `null` or `undefined`.
- Response DTOs map fields explicitly; never send a database row, it holds encrypted credentials.
- Installer errors the user should read go through `ui.error()` from `src/lib/ui.ts`, then `process.exit(1)`; throw for unexpected conditions.
- AWS resource names come from `utils/naming.ts` (`lancer-` prefix) and tags from `utils/tags.ts`; never write a name or a tag by hand.
- Tests: API `*.spec.ts` beside the code, controllers through `app.inject` with adapters mocked by `vi.mock` and fixtures; infrastructure `*.test.ts`.
- File names in kebab-case.
